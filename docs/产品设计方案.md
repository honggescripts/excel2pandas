# excel2pandas 产品设计方案

> **第一版**
>
> 本方案以**一个真实的多层报价测算模板**的实测结果为准编写。
> 该模板的规模指标（列数、依赖深度、外部表数量等）保留在文中作为论据，
> 但**全部业务字段名、内部表名、定价参数与数据记录均已移除**，不构成业务信息披露。
>
> 仓库内 `examples/` 是一份**完全虚构的电商定价案例**，用于展示产物形态，可复现运行。

---

# 第一部分 产品定位

## 1.1 一句话

> 读一遍 Excel 模板的样板行公式，生成一份**自包含的 Python 文件**，用它批量跑任意多条记录，最后**逐格对账**——证明生成代码没有算错。

## 1.2 边界（north star）

**是**：一次性把「公式驱动的一行」翻译成 pandas 表达式 + 可维护的 `CONFIG`。

**不是**：

- ❌ 通用 Excel 转换器（只做「模板测算表」，不做自由手工表格）
- ❌ 执行引擎 / 公式解释器（不运行时解析 Excel）
- ❌ 双向同步（改 Python 不回写 Excel）
- ❌ Excel 的替代品（对账基线仍来自 Excel）

判断标准：**凡是让「生成的代码变复杂」的需求，都要先问一句「这个模板真的需要吗」。**

这条标准实际砍掉了 6 项看似合理的设计：

| 被砍掉的设计 | 砍掉理由 |
|---|---|
| 独立的 `cache` 模块 + 复杂失效逻辑 | generate 只读一次表，20 行文件指纹足够 |
| 独立的 `preflight.md` 报告 | 内容本就是 `migration_report.md` 的一部分 |
| `plugins` / `cache` 两条 CLI 子命令 | 实测无使用场景，过度设计 |
| 跨工作簿引用归一化 | 实测模板无跨工作簿引用，缺口不存在 |
| 模块级 `models.py` 集中数据类 | 20 个数据类集中反而制造循环依赖 |
| `layer` / `dependency` / `plugin` 独立模块 | 与宿主模块共用同一次遍历或同一批公式，拆开只增加开销 |

## 1.3 两级主入口

**生成器入口（3 个必填参数）**

```python
generate(excel_path, sheet_name, target_row)
```

**生成代码的入口（3 参数）**

```python
def calc(primary_values, file_paths=None, inputs=None):
    """
    primary_values : 主键值列表（批量时可一次传一批）
    file_paths     : 文件路径字典，{"main": "...xlsx"}
    inputs         : 手填参数列的逐行覆盖值   ← 见 §3.2
    """
```

## 1.4 产品哲学

| 原则 | 含义 | 为什么 |
|---|---|---|
| **不阻断生成** | 任何单列失败 / 结构问题 / 语法错误，都不阻断文件产出 | 半成品 > 拿不到东西 |
| **标注 + 建议** | 失败处不是简单 NaN，而是原因 + 原公式 + 缓存值 + 修复建议 | 人工修复不做二次挖掘 |
| **起点不是成品** | 用户拿到的可能不能直接跑，简单修改后就能用 | 迁移是渐进过程 |
| **对账即验收** | 没有 `verify_report.md` 一致率支撑的生成，不算完成 | 唯一能证明「没算错」的机制 |

# 第二部分 架构

## 2.1 五模块结构

```
excel2pandas/
├── reader.py      读簿 → SheetModel（列/表头/单元格/分层/依赖/评估报告）
├── converter.py   拓扑排序 → 公式 → pandas 表达式（含函数注册表）
├── generator.py   编排 + 渲染 .py + 报告 + 缓存
├── runner.py      执行（单条 / 批量 / 分块 / 断点续传 / 异常映射）
├── verifier.py    逐格对账 → diff 报告
├── _runtime.py    运行时辅助库（模板资源，会被嵌入生成代码）
└── __main__.py    CLI 路由壳（≤190 行，无业务逻辑）
```

## 2.2 数据流

```
Excel 模板
    ↓
[reader]      双读（公式 + 缓存值）→ 列建模 → 3+1 层分类 + 冲突检测
    ↓
[converter]   分词 → AST → 逐列转换（跨表操作提升为临时列）→ CONFIG 抽取
    ↓
[generator]   渲染自包含 .py（内嵌 runtime）+ business_rules.md + migration_report.md
    ↓
generated_code.py
    ↓                                    ↓
[runner] 批量执行                  [verifier] 逐格对账
    ↓                                    ↓
result.xlsx / progress.json         verify_report.md
```

**关键点**：生成代码是**自包含**的——`_runtime.py` 里被用到的那部分 helper 会**内嵌进生成文件**。用户拿走的 `.py` 不需要安装本包就能跑。

## 2.3 模块职责与边界

| 模块 | 职责 | **不负责** |
|---|---|---|
| `reader.py` | 双读目标 sheet、列建模与列名唯一化、分层分类 + 冲突检测、迁移评估报告 | 公式转换、代码生成、执行 |
| `converter.py` | 分词 + 递归下降解析 → AST；AST → pandas 表达式；跨表操作提升为临时列；函数注册表；全局拓扑排序；CONFIG 抽取 | 文件 IO、代码渲染、执行 |
| `generator.py` | 串 reader → converter；渲染 .py（内嵌 runtime）；business_rules.md；委托 reader 出 migration_report.md；Excel 指纹缓存 | 执行、对账 |
| `runner.py` | 单条 / 批量 / 分块 / 断点续传 / **异常映射回 Excel 列** | 代码生成、对账 |
| `verifier.py` | 逐记录 + 逐字段 diff；Excel 侧错误分类；容差分级 | 代码执行、代码生成 |
| `_runtime.py` | 约 40 个 `_xxx` 运行时 helper（Excel 语义复现：`_round` / `_ceiling` / `_cumipmt` / `_lookup` / `_aggif` …） | 一切设计期逻辑 |

> 为什么 `verifier` 不折进 `runner`：对账是这个项目**唯一能证明「生成代码没写错」的机制**。把它和执行放在同一个模块里，等于让运动员给自己当裁判。

## 2.4 为什么是 5 个模块

| 新模块 | 合并来源 | 合并依据 |
|---|---|---|
| `reader` | `reader` + `layer` + `assessor` | 三者都只做「读 Excel → 出元信息」，共用**同一次双读遍历**。拆开 = 把整本工作簿的全表扫描重复 3 遍 |
| `converter` | `dependency` + `converter` + `plugin` | `dependency` 只做拓扑排序，输入输出都是公式集合；`converter` 本就需要拓扑序；`plugin` 只是转换时查的一张函数表。三者共用同一批公式 = 天然一体 |
| `generator` | `generator` + `renderer` + `reporter` + `cache` | 渲染是 generator 的**私有步骤**，没有第二个消费者；报告各归其产生者；缓存只是 20 行文件指纹 |
| `runner` | `runner` | 执行层，独立生命周期 |
| `verifier` | `verifier` | 对账独立性是核心价值，不与 runner 合并 |
| — | `models` / `config` | 拆散进各模块，常量按归属就地定义 |
| `__main__.py` | `cli` | 纯 argparse 路由，不计入 5 模块 |

> 如果一定要压到 4 个：把 `verifier` 折进 `runner`。**不建议**，理由见 §2.3。

# 第三部分 核心设计决策

## 3.1 执行顺序 = 全局拓扑排序，分层只作统计

| 方案 | 规则 | 评价 |
|---|---|---|
| 直觉做法 | 分层冲突时**按分层顺序继续生成 + 加注释标注** | ❌ 会静默算错 |
| **本方案** | **冲突即降级为全局拓扑排序** | ✅ 正确性优先 |

**为什么不按分层顺序输出**：实测模板的 105 列里有 **6 处跨层反向依赖**（低层列引用了高层列）：

```
L2 的列 W  → L3 的列 G          L1 的列 AP → L3 的列 AO
L2 的列 X  → L3 的列 G          L2 的列 AL → L3 的列 AI
L2 的列 AM → L3 的列 G          L1 的列 CA → L2 的列 S
```

按分层顺序输出，`df["W"] = … df["G"] …` 会排在 `df["G"]` 赋值之前。因为数据加载阶段已把 G 列读入（全 NaN），**pandas 不报错，静默算出错误结果**。

> 这不是「可读性 vs 正确性」的取舍，是拿可读性换正确性。分层产出保留，但只进 `migration_report.md` 当统计说明。

## 3.2 手填列 = 输入锚点 → `calc()` 必须三参数

**实测**：值列里有相当一部分是**人工输入且被下游大量引用**（手工定价、固定费用、服务费标准这类）。它们往往是 2~4 个公式列的直接输入。

**问题**：批量跑不同记录时，每行的用手填值都不同——**不可能「从 Excel 固定读」**。

**决策**：数据列不能简单地「从 Excel 读、不生成赋值」。样板行手填值写进 `CONFIG` 作**默认值**，`inputs` 逐行覆盖：

```python
df = pd.DataFrame({'商品编号': pks})
df['成本价'] = _inputs('成本价', pks, default=_DEFAULTS['成本价'])   # inputs 优先，否则用默认值
```

判据也要注意：**判断一列是不是数据列，看它在样板行上有没有公式**，不能看公式长什么样。`=3900` 这种纯字面量公式在语义上是「数据」，按公式外观判断会误分类。

## 3.3 公式解析：tokenizer + 递归下降 AST

**为什么不"字符串剥离 + 正则"**：直觉方案是「用占位符剥离字符串字面量 + 按逗号分隔（注意嵌套括号）+ 字符串里的 `VLOOKUP(` 不算函数调用」——这三句话每一句都是在给手写字符串扫描器打补丁。

**实测真实语法噪声**：

| 噪声 | 规模 | 正则能否硬吃 |
|---|---|---|
| `_xlfn.` 前缀 | 26 处 XLOOKUP 全带 | 勉强 |
| `$W2` 锁列 / `AR$1` 锁行（表头行引用 = 常量） | 7 处 | 勉强 |
| 整列引用 `B:B` | 26 处 | 勉强 |
| `0` 代 `FALSE` | 12 处 VLOOKUP | 可行 |
| `VLOOKUP(E:E, …)` 用整列当查找值 | 3 处 | ❌ 必炸 |

**方案**：`tokenize()` → 递归下降 `Parser`（`expr → cmp → concat → add → mul → unary → power → postfix → primary`）→ AST 节点（`Num / Str / Bool / ErrLit / Ref / Range / Unary / BinOp / Call / MapTable`）→ 在 AST 上做转换。

好处：「字符串里的函数名」「嵌套参数分隔」「括号配对」「`_xlfn.` 剥离」全部**天然正确**。代价约 250 行，但省掉它，后面每加一个 Excel 函数都要打补丁。**这是唯一值得多花钱的地方。**

## 3.4 跨表操作：运行时 helper + 位置对齐数组

**为什么不生成 merge**：直觉写法是

```python
df["保险成本"] = df[["分组"]].merge(df_成本表[…], …)["保险成本"].values
```

`.values` 依赖「右表无重复键 + 行序完全一致」。实测外部表是 1 万～9 万行台账，**主键重复是常态**，一重复就抛长度不匹配。

**实际实现**：跨表操作**不在生成代码里做 merge**，而是封装进运行时 helper，helper 返回**与主表行序位置对齐的 ndarray**：

```python
# 生成代码里的真实形态（examples/generated_code.py 节选）
df['__tmp_lk_01'] = _lookup(_sheet('运费价目'), 'A', 'B', df['类目'], not_found=None)
df['头程运费'] = df['__tmp_lk_01']

df['__tmp_ag_33'] = _aggif(_sheet('服务记录'), 'N', [('F', df['商品编号'])], 'sum')
df['服务成本'] = df['__tmp_ag_33']
```

helper 内部：`建 key→value 索引 Series → drop_duplicates(keep="first") → Key 序列 .map(索引) → to_numpy()`。

**为什么这个设计更好**：

1. **根本没有 merge**，所以不存在行序被打乱的问题 → 不需要 `_row_id` 兜底重排；
2. 重复键在 helper 内按 **Excel 首次命中语义**（`keep="first"`）处理，与 VLOOKUP/XLOOKUP 行为一致；
3. 跨表逻辑集中在 `_runtime.py` 一处，生成代码只留一行调用，可读性好。

**代价（已知，可接受）**：重复键被**静默取首条**，会掩盖外部台账的数据质量问题（已列入 §10 二期）；每次 lookup 都重建索引，相同 `(sheet, key列, value列)` 组合未做记忆化。

## 3.5 三分类输出

| 类型 | 生成代码 | 输出 df 列名 |
|---|---|---|
| 数据列 | 不生成赋值（作为输入参数） | 原列名 |
| 成功列 | 生成赋值语句 | 原列名 |
| 失败列 | **不生成赋值，保留 Excel 兜底值** | 原列名 + **`_fail` 后缀** |

失败列不填 `NaN`，而是**保留 Excel 缓存兜底值 + 列名加 `_fail`**——这样批量跑出来的 df 仍然可用，且一眼看出哪些列不可信。

## 3.6 魔法值常量 → `CONFIG`

| 类型 | 归属 | 例子 | 处理 |
|---|---|---|---|
| **原表常量** | 数据层 | 单元格本身就是 3900 | 读 Excel，或进 `inputs` |
| **魔法值常量** | 配置层 | 公式里嵌的 `1.13` / `3600` | 抽到 `CONFIG` 字典 |

原表常量是**数据**，改它等于改数据；魔法值常量是**规则**，改它是业务决策。分开后，改规则只改 `CONFIG`。

命名优先级：`config_names.json`（用户指定）→ `DEFAULT_CONFIG_NAMES` 示例映射 → 启发式（`1.xx`/`0.xx` → `_rate_*`、整数 ≥1000 → `_fee_*`）→ 序号兜底。

> ⚠️ **映射表的键格式坑**：键由 `_skey(值)` 生成，**小数点写成下划线**（`1.13 → "1_13"`、`0.05 → "0_05"`、`-0.5 → "neg0_5"`）。
> 写成 `"1.13"` 永远查不到——查找侧走 `_skey()`，键必须同格式。这个格式不一致曾导致映射表对所有小数常量静默失效。

## 3.7 失败不阻断生成

| 场景 | 处理 |
|---|---|
| 单列转换失败 | 保留 Excel 兜底值 + `_fail` 后缀 + 原因 + 原公式 + 缓存值 + 修复建议，继续 |
| 分层冲突 | 自动降级为全局拓扑排序，继续 |
| 循环引用 | 拓扑排序直接报错并列出环上的列 |
| Excel 侧错误值 | 单独归类，不参与一致率分母 |
| AST 校验失败 | 头部警告 + 写文件 + 抛异常 |
| 读 Excel 失败 | 写最小文件 + 抛异常 |

## 3.8 缓存：Excel 指纹

```python
sha256(f"{绝对路径}|{文件大小}|{mtime}|{sheet}|{样板行}|{VERSION}")[:16]
```

Excel 未变则跳过生成，`--force` 强制重跑。**不引入独立 cache 模块**——generate 只读一次表，成本一次性，把缓存键设计成含 `header_row` / `target_row` / `parser_version` 的复杂失效逻辑没有收益。

# 第四部分 Excel 语义陷阱清单

**这一节是本方案最核心的工程资产——每一条都是实测踩出来的。**

| # | 陷阱 | 表现 | 处理 |
|---|---|---|---|
| 1 | `_xlfn.` 前缀 | openpyxl 读新版函数带前缀（`_xlfn.XLOOKUP`） | 解析时剥前缀。**否则 26 处 XLOOKUP 全部失败** |
| 2 | lookup 列索引越界 | `VLOOKUP(A2,'台账'!B:H,8,0)`——`B:H` 只有 7 列却取第 8 列 | 按「从起始列偏移 7 列」自动纠正，并在 `business_rules.md` 标红提示人工确认 |
| 3 | 文本数字隐式转换 | 单元格是文本 `'7.5%'`，参与财务函数计算 | 只在「模板缓存值本身就是数字样式文本」的列上加 `_n()`，不滥用。**不加则 `'7.5%'/12` 直接 TypeError** |
| 4 | 聚合函数无匹配语义不同 | — | `SUMIFS/COUNTIFS/MAXIFS/MINIFS` → **0**；`AVERAGEIFS` → `#DIV/0!` → **NaN**；`XLOOKUP/VLOOKUP` → `#N/A` → **NaN**。混同则批量结果整片 NaN |
| 5 | `ROUND` 不是 numpy 的 round | Excel 远离零舍入 vs numpy 银行家舍入 | `ROUND(2.5,0)`：Excel=3，numpy=2。用 `_round/_roundup/_rounddown` 复现 |
| 6 | Excel 侧错误值污染对账基线 | pandas 把 `#REF!`/`#N/A` 读成 NaN，被误判成「空值」或「逻辑差异」 | verifier 额外用 openpyxl 读**原始缓存值**，把这类单元格归为 **Excel侧错误**，不计入一致率分母 |
| 7 | 锁定引用语义 | `$W2` 锁列 / `AR$1` 锁行 | 锁列不锁行 → 正常同行引用向量化；**锁第 1 行（表头行）→ 取表头值成为常量**（`AR$1` 的值进 CONFIG） |
| 8 | 整列引用 | 26 处用 `B:B` 而非 `A:C` | 支持整列；`VLOOKUP(E:E, …)` 用整列当查找值时归一化为「当前行的 E 值」 |

## 4.1 被踩出来的模板 Bug（真实案例）

| Bug | 公式（已脱敏） | 后果 |
|---|---|---|
| **VLOOKUP 越界** | `=VLOOKUP(A2,'台账'!B:H,8,0)` | Excel 返回 `#REF!`，**连锁污染下游 7 列**。其中两列是整条计算链的根 |
| **错误值嵌套** | — | `#N/A` 污染 4 列；`#NUM!` 污染利息类列（财务函数无解） |
| **文本当数字** | `=CUMIPMT(CE2/12, …)`，而 `CE` 是文本 `'7.5%'` | Excel 隐式转 0.075，Python 不加处理直接 TypeError |

> **处理原则**：生成器**按正确逻辑算**（取第 9 列的正确字段），对账器把 Excel 侧的 `#REF!` 归为「Excel 侧错误」。**不按 Excel 的错值对齐**——否则修好 Bug 后 Python 算出真实值反而被判为「逻辑差异」。

# 第五部分 支持的边界

## 5.1 支持（内置 42 个函数）

| 类别 | 覆盖 |
|---|---|
| 算术/比较 | `+ - * / ^ %`、`= <> < > <= >=`、字符串拼接 `&` |
| 逻辑 | `IF / IFS / AND / OR / NOT / IFERROR / IFNA`（数组感知，逐元素） |
| 数学 | `ABS / INT / ROUND / ROUNDUP / ROUNDDOWN / CEILING / FLOOR / SQRT / MOD / POWER / MAX / MIN / SUM / PRODUCT` |
| 文本 | `VALUE / TEXTBEFORE / TEXTAFTER / CONCAT / CONCATENATE / TRIM / LEFT / RIGHT / LEN / TEXT` |
| 引用 | `ROW / COLUMN`、同表引用、`$` 绝对/混合引用、表头行引用（`$A$1`） |
| 查找 | `XLOOKUP`（含反向 / `if_not_found`）/ `VLOOKUP`（精确）/ `INDEX+MATCH` |
| 条件聚合 | `SUMIFS / COUNTIFS / AVERAGEIFS / MAXIFS / MINIFS` |
| 财务 | `RATE / FV / PV / PMT / NPER / IPMT / CUMIPMT`（`numpy_financial` + 自实现 `cumipmt`） |

## 5.2 不支持 → 失败列 + `_fail` 后缀 + 报告说明

| 类别 | 说明 |
|---|---|
| 跨工作簿引用 `[Book1.xlsx]Sheet1!A1` | 实测模板无此需求，缺口不存在 |
| 同表跨行引用 | 仅支持上一行 `shift(1)`，其余失败 |
| 数组公式 / 动态数组 | 建议拆成多列计算 |
| `TEXT` 格式化 | 格式规则无法自动翻译 |
| 命名区域 | — |
| 循环引用 | 拓扑排序直接报错，列出环上的列 |

## 5.3 新增函数（插件接口）

```python
from excel2pandas.converter import register_function

@register_function("MY_FUNC")
def _f_my_func(args, node, ctx):
    return f"_my_func({', '.join(args)})"
```

对应补 `_runtime.py` 里的运行时实现；`generated_code.py` 会内嵌被用到的 helper。

## 6.1 `generated_code.py` 结构

以 `examples/generated_code.py` 为准（真实产物，可直接查看）：

```python
CONFIG = {
    "含税系数": 1.13,
    "年化费率": 0.06,
    "_rate_0_05": 0.05,          # 未命中命名映射 -> 启发式命名
    "_rate_1_2": 1.2,
    "_rate_0_3": 0.3,
}

# 源文件路径：换数据源只改这里
FILE_PATHS = {
    "main": r"examples\demo_template.xlsx",
}

def calc(primary_values, file_paths=None, inputs=None):
    df = pd.DataFrame({'商品编号': pks})

    # ---- 数据层：手填输入参数 ----
    df['成本价'] = _inputs('成本价', pks, default=_DEFAULTS['成本价'])

    # ---- L2 ----
    # G2: =VLOOKUP(C2,运费价目!$A:$B,2,0)
    df['__tmp_lk_01'] = _lookup(_sheet('运费价目'), 'A', 'B', df['类目'], not_found=None)
    df['头程运费'] = df['__tmp_lk_01']

    # ---- L3 ----
    # H2: =ROUND(E2*1.13,2)
```

## 8.4 性能

生成的代码是**向量化**的（跨表 lookup / 聚合由 `_lookup` / `_aggif` 一次性映射到全表），不是逐条循环。

| 项 | 实测值 |
|---|---|
| 批量 50 条记录 | **≈ 30 秒**（含首次读取 13 张外部表） |
| 分块 | `run_batch` 按 chunk（默认 200 条）调用 `calc`，工作簿句柄与 sheet 缓存跨 chunk 复用 |

> **性能结论**：跨表查找全是对 1 万～9 万行表的查找。**必须向量化**（一次映射全表），按主键逐条查找会直接跑死。

## 附录 A：验收口径

一份迁移只有同时满足以下三条，才算「完成」：

1. **转换覆盖率**：公式列转换成功数 / 公式列总数 —— 真实项目实测 79/79；
2. **一致率**：排除 Excel 侧错误后的逐格一致率 —— 真实项目实测 100.00%；
3. **可批量**：生成的代码能直接跑 N 条主键并产出结果表 —— 实测 50 条 ≈ 30 秒。

缺任何一条都不算完成。**其中第 2 条是不可替代的**——它是对「生成代码是否算错」的唯一客观证据。

## 附录 B：本方案的自我修正记录

设计过程中有三处最初写错、后经读码核对纠正，记录在此以说明本方案的验证标准：

| 最初写的 | 实测后改为 |
|---|---|
| 跨表操作「临时列 + merge，需 `_row_id` 兜底重排」 | 实际是运行时 helper 返回**位置对齐数组**，**0 处 merge**，因此不存在行序问题，也不需要 `_row_id`。这个实现比 merge 方案更稳 |
| 「重复键 → 报失败列」 | 实际按 Excel 首次命中语义 `keep="first"` 静默取首条（数据质量问题列入二期） |
| 常量命名映射键写作 `"1.13"` | 实际查找走 `_skey(值)`，键必须是 `"1_13"`。原格式导致映射对**所有小数常量从未生效**，已修正 |

**结论**：凡涉及「实现到底怎么做」的断言，必须先读代码再落笔；凡涉及规模与效果的断言，必须有可复现的实测数据支撑。
